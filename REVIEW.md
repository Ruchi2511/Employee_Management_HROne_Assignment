# REVIEW.md

List every defect you found in the starter `app/main.py` (helpers and endpoints). For each one:

Line numbers refer to the original starter file.

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `MongoClient(...)`, line 22 | The client isn't timezone-aware, so datetimes come back from MongoDB with no timezone. | Read back a `punch_in` and `tzinfo` is `None`. Any conversion that assumes local time is off by the server's UTC offset. | Added `tz_aware=True`. Every datetime in the app is now UTC-aware. |
| 2 | `MongoClient(...)`, line 22 | It uses the default 30-second server selection timeout. | Stop MongoDB and call an endpoint that queries it, like `GET /employees`: it hangs for about 30 seconds before failing. (`/health` doesn't touch MongoDB, so it still returns 200; see #25.) | Set `serverSelectionTimeoutMS=5000`. |
| 3 | Whole file | No indexes are created, so nothing enforces a unique `emp_code` or one record per employee per day, and every query scans the collection. | Two parallel creates with the same `emp_code` both get stored. `explain()` on the list query shows `COLLSCAN`. | Added `ensure_indexes()`, which runs at startup from the FastAPI lifespan. It creates two unique indexes and four query indexes and is safe to run repeatedly. |
| 4 | `compute_late_minutes`, line 37 | It rounds down to minutes and then checks `> 10`. Exactly 10:00 after shift start is correctly on time, but 10:01 to 10:59 after should be late and is treated as on time. | Shift 09:30, punch at 09:40:30. Expected 10, got 0. | It now compares seconds (`> 600`) and only then floors to minutes. |
| 5 | `compute_late_minutes`, line 35 | `punch_in.replace(hour, minute)` builds the shift start in the server's local timezone, not IST, so the result depends on where the server runs. | On a UTC server, for example: punch at 10:05 IST (04:35Z) on a 09:30 shift. The start becomes 09:30 UTC, so the punch looks early. Expected 35, got 0. | Added `shift_start_at()`, which builds the shift start in IST on the attendance date. |
| 6 | `compute_late_minutes` and `punch_in`, lines 35 and 103 | Overnight shifts aren't handled. A punch after midnight is compared with the same calendar day's shift start and gets the wrong date. | Shift 22:00-06:00, punch at 00:30 IST. Expected date = the previous day and 150 late minutes. Got the punch's own calendar date and 0. | Added `attendance_date()`. If `shift_end <= shift_start` and the IST time is before `shift_end`, the record belongs to the previous day. Lateness is measured from that day's shift start. |
| 7 | `punch_in`, lines 102-103 | `datetime.fromtimestamp()` gives naive server-local time. The date is the server's local date, not the IST date, the instant isn't truncated to whole seconds, and PyMongo stores the naive value as if it were UTC. | On a UTC server, a punch at 00:30 IST gets the previous day's date. On an IST server, a punch at 04:35Z is stored as 10:05Z, 5.5 hours off. A punch sent as `...900` ms is stored and returned with the milliseconds. | `ms_to_datetime()` converts to UTC and drops the sub-second part. The date comes from `attendance_date()` in IST. |
| 8 | `PunchInIn.punched_at`, line 65; `punch_in`, line 102 | `Optional[int]` is lax. It accepts numeric strings, whole floats, seconds-sized numbers and booleans. `if body.punched_at` also treats 0 as missing. | `"1783312500000"`, `1783312500000.0`, `1783312500` and `true` (which becomes 1) are all accepted instead of returning 422. `punched_at: 0` quietly uses the current time. | Used a strict `EpochMillis` type: integer only, range 100000000000 to 4102444800000. Leaving it out still means "now". |
| 9 | `PunchInIn.status`, line 66 | `status: str` accepts anything, including `ABSENT`, `LEAVE` or a typo. | Punch in with `"status": "FOO"` and it gets stored. | Limited it to `PRESENT`, `WFH` and `ON_DUTY`. Anything else is a 422. |
| 10 | `punch_in`, lines 101 and 113 | It never checks whether the employee exists, so `emp["shift_start"]` fails on `None`. | Punch in with an unknown `emp_code` and you get a 500. | Returns 404 when the employee isn't found. |
| 11 | `punch_in`, line 104 | Check-then-insert: it looks for an existing record and then inserts. Two requests at the same moment can both pass the check. | Fire parallel punch-ins for the same employee and day. Because it checks before inserting and there's no unique index, you can get more than one 201 and duplicate records. | Removed the check. It inserts directly and relies on the unique `{emp_code, date}` index. A `DuplicateKeyError` becomes a 409. |
| 12 | `punch_in`, line 119 | The response includes an `id` field and returns `punch_in` as a datetime string. The contract has no ids and uses epoch milliseconds. | The response has `"id": "66a..."` and `"punch_in": "2026-07-06T..."`. | It now returns `serialize_attendance()`, which has exactly the contract fields with times in ms. |
| 13 | `EmployeeIn`, lines 53-60 | No validation on any field. | `shift_start: "25:99"`, `emp_code: "abc"`, `joined_on: "2026-02-30"`, or the same start and end time are all accepted. | Added the contract's patterns and lengths, a real calendar-date check on `joined_on`, and a check that `shift_start` differs from `shift_end`. |
| 14 | `create_employee`, line 79 | Check-then-insert again, so concurrent creates with the same `emp_code` can both succeed. | Send the same create from several threads at once and get several 201s. | It inserts directly, relies on the unique `emp_code` index, and returns 409 on `DuplicateKeyError`. |
| 15 | `create_employee`, line 82 | `datetime.now()` is naive local time. PyMongo stores naive datetimes as if they were UTC, and the response returns an ISO string, not epoch ms. | On an IST machine the stored `created_at` is 5.5 hours off. The response has `"created_at": "2026-..."`. | Uses `utc_now()` and returns `created_at` as epoch ms through `serialize_employee()`. |
| 16 | `list_employees`, line 93 | `skip = page * page_size` skips a whole page. | With 5 employees, `GET /employees?page=1` returns nothing. | Changed to `(page - 1) * page_size`. |
| 17 | `list_employees`, line 94 | `total` counts the whole collection and ignores the department filter. | Filter by a department with 2 people out of 7 and you get `total: 7`. | Counts with the same filter as the query. |
| 18 | `list_employees`, line 95 | There's no sort, so the page order isn't guaranteed and paging can repeat or skip rows. | The order changes with insert order. The contract says to sort by `emp_code`. | Sorts by `emp_code` ascending in MongoDB, backed by an index. |
| 19 | `list_employees`, line 89 | `page` and `page_size` have no limits. | `page=0` and `page_size=1000` are accepted, `page_size=0` returns every employee, and `page=-1` gives a 500. | `page >= 1` and `1 <= page_size <= 100`. Anything else is a 422. |
| 20 | `list_employees`, line 95 | Items return `created_at` as a datetime, not epoch ms. | `created_at` comes back as an ISO string. | Each item goes through `serialize_employee()`. |
| 21 | `compute_work_hours`, line 41 | `round()` isn't half-up. It uses float maths and rounds halves to even. | 9h 07m 30s is exactly 9.125 hours. Expected 9.13, got 9.12. | Works on whole seconds with `Decimal` and `ROUND_HALF_UP`. |
| 22 | `compute_overtime`, line 47 | There's no 30-minute minimum. Any time after shift end counts. | Shift ends 18:30, punch out at 18:35. Expected 0, got 5. | Floors to whole minutes, then returns 0 unless it's at least 30. |
| 23 | `compute_overtime`, line 46 | The shift end is always put on the attendance date, so an overnight shift ends a day too early. | Shift 22:00-06:00 starting on the 6th, punch out at 06:40 on the 7th. Expected 40, got 1480. | Added `shift_end_at()`, which moves the end to the next day when `shift_end <= shift_start`. |
| 24 | `compute_overtime`, line 47 | It subtracts an IST-aware shift end from `punch_out`, which is naive everywhere else in the starter. | Calling it with the starter's naive punch time raises `TypeError: can't subtract offset-naive and offset-aware datetimes`, which would be a 500. | All datetimes are UTC-aware now (client `tz_aware=True` and the time helpers), and the time is truncated to whole seconds first. |
| 25 | `health`, lines 72-74 | It returns 200 without asking MongoDB. The contract says 200 only when MongoDB answers a ping, otherwise 503. | Stop MongoDB and `/health` still says `{"status": "ok"}`, so the readiness check passes on a dead app. | Pings with `admin.command("ping")` under a 2-second `pymongo.timeout`. Any `PyMongoError` returns 503 `database unavailable`, without the exception text. |
| 26 | `list_attendance`, lines 144-146 | It loads every matching record into Python, then sorts, counts and slices there. | With ~100k records each page reads the whole collection; `GET /attendance` with no filters does a `COLLSCAN` and gets slower as data grows. | `count_documents` with the filter for `total`, and `find` with sort, skip and limit in MongoDB, backed by the `{date: -1, emp_code}` index. |
| 27 | `list_attendance`, line 145 | It sorts by `date` only. The contract sorts by `date` descending, then `emp_code` ascending. | Insert EMP0003, EMP0001, EMP0002 for the same date in that order and they come back in insertion order, not EMP0001, EMP0002, EMP0003. | Sorts on `[("date", -1), ("emp_code", 1)]`. |
| 28 | `list_attendance`, lines 130-131 | `page` and `page_size` have no limits. | `page=0`, `page=-1`, `page_size=0` and `page_size=1000` all return 200; `page=-1` even returns rows from the wrong end of the list. | `page >= 1` and `1 <= page_size <= 100`. Anything else is a 422. |
| 29 | `list_attendance`, lines 127-128 | `date_from` and `date_to` aren't validated, and a reversed range isn't rejected. | `date_from=2026-02-30` or `07/01/2026` is compared as a plain string and returns wrong rows; `date_from=2026-07-31&date_to=2026-07-01` returns an empty 200 instead of 422. | `YYYY-MM-DD` pattern plus a real calendar-date check, and `date_from > date_to` is a 422. |
| 30 | `list_attendance`, line 129 | `status` accepts any string. | `status=FOO` or `status=present` returns an empty 200 instead of 422. | Limited to the five contract statuses. |
| 31 | `list_attendance`, lines 148-150 | Items are raw MongoDB documents: they add an `id`, return times as datetimes, and legacy records lack `half_day` and `history`. | Response items have `"id": "66a..."`, `"punch_in": "2026-07-06T..."`, and the sample legacy record has no `half_day`. | Excludes `_id` and serializes each item with `serialize_attendance()`: times in epoch ms, `half_day` false and `history` `[]` when missing. |

Also note anything you looked at and decided was **not** a defect, and why.

- `load_dotenv()` doesn't override variables that are already set, so real environment variables win over `.env`. That's what the contract asks for.
- The sync `def` endpoints with PyMongo are fine. FastAPI runs them in a thread pool, so they don't block the event loop.
- In `list_attendance`, the offset `(page - 1) * page_size` is correct, unlike the one in `list_employees`.
- In `list_attendance`, comparing dates with `$gte`/`$lte` works, because valid, consistently formatted `YYYY-MM-DD` strings sort in date order. The missing validation of `date_from`/`date_to` is a separate defect (#29).
